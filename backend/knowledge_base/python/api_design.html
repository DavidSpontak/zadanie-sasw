REST API Design Best Practices

Resource Naming

Use nouns for resources, not verbs. Resources should be plural.


# GOOD
GET /users
GET /users/123
POST /users
PUT /users/123
DELETE /users/123

# BAD
GET /getUser
POST /createUser
GET /user/getAll

HTTP Status Codes

  • 200 OK – Successful GET, PUT, PATCH
  • 201 Created – Successful POST that created a resource
  • 204 No Content – Successful DELETE
  • 400 Bad Request – Client sent invalid data
  • 401 Unauthorized – Authentication required
  • 403 Forbidden – Authenticated but not authorized
  • 404 Not Found – Resource does not exist
  • 422 Unprocessable Entity – Validation errors
  • 429 Too Many Requests – Rate limit exceeded
  • 500 Internal Server Error – Unexpected server failure

Versioning

Always version your API from day one. Prefer URL versioning for discoverability.


# URL versioning (recommended)
/api/v1/users
/api/v2/users

# Header versioning (alternative)
Accept: application/vnd.myapi.v2+json

Pagination


# Cursor-based (preferred for large datasets)
GET /users?cursor=abc123&limit=20

# Offset-based (simpler but less scalable)
GET /users?page=2&per_page=20

# Response envelope
{
  "data": [...],
  "pagination": {
    "next_cursor": "def456",
    "has_more": true,
    "total": 1500
  }
}

Error Response Format


{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid email address",
    "field": "email",
    "request_id": "req_abc123"
  }
}

Authentication

Use Bearer tokens in the Authorization header. Never pass secrets in URL query params.


# CORRECT
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9...

# WRONG - token in URL is logged by proxies/servers
GET /api/users?token=eyJhbGciOiJIUzI1NiJ9...

Rate Limiting Headers


X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 456
X-RateLimit-Reset: 1716825600
Retry-After: 3600

Idempotency

POST endpoints should support idempotency keys to prevent duplicate operations.


POST /payments
Idempotency-Key: client-generated-uuid-abc123
